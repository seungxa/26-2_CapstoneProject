- 상태: **초안(2026-11-14)**, 사용자 검토 전.
- 작업 기준: 팀 저장소 `seungxa/26-2_CapstoneProject`의 `codex/practice-track-integration`(PR #1, `4da2814`) 위에 만든 `feature/local-ai-gaze-direction`.
- 범위: 세 갈래의 작업을 한 문서에 담는다. A 팀 통합 준비, B OpenAI 제거와 로컬 꼬리질문·무료 서버, C 시선 방향 분석. 구현 계획은 갈래별로 따로 쓴다.

## 0. 왜 하는가

- **최종 제품의 모습.** 사용자가 크롬 확장과 팀 웹을 내려받아 자기 노트북에서 쓰는 취업 준비 서비스다. 세 팀원의 작업은 결국 팀 저장소 하나로 합쳐져야 한다.
  - dlrkdms323: `feature/frontend`, Supabase 로그인·프로필.
  - seungxa: `chrome-extension`, 지원서 자동 입력 확장.
  - 본인: ② Practice·③ Track.
- **팀 결정.** OpenAI 같은 유료 외부 API를 쓰지 않는다. 필요한 처리는 라이브러리를 import해서 직접 돌린다.
- **시선 분석의 목적.** 면접의 비언어적 습관을 짚어 주는 것이다. 예를 들어 대본을 보느라 아래를 보거나, 시선이 옆으로 흔들리는 습관이다. 정밀한 판정(렌즈를 봤나, 화면 위쪽을 봤나, 32px 영역을 봤나)은 필요 없고, 시선이 대략 어느 방향인지만 알면 된다.
- **2026-11-14 확인한 현황**
  - 팀 저장소 `main`은 초기 커밋뿐이다.
  - PR #1은 미머지 상태이고 리뷰가 0건이다.
  - 백엔드 DB 기본값은 로컬 SQLite다. Supabase Postgres도 지원하지만 실제 클라우드에 연결한 적은 없다.
  - OpenAI 호출 경로가 아직 남아 있다: 맞춤 질문, AI 코칭, 꼬리질문, 디브리프 요약, AI 피드백, OpenAI 전사.
  - 시선 G1·G2는 2026-11-03 실측에서 실패했다.
    - G1: 처음 보는 응시 AUC 0.37, 렌즈 응시 toward 0%.
    - G2: 오차 중앙값 181px, 뷰포트 너비의 19%.

## 1. 목표 · 하지 않는 것 · 실패로 보는 것

**목표**
- **A 팀 통합 준비.** 팀원 코드를 고치지 않고 합칠 준비를 끝낸다.
  - 팀 Supabase에 적용할 SQL 묶음과 연결 점검 도구를 만든다.
  - 크롬 확장 통합 계약 문서를 쓴다.
- **B 로컬 AI.**
  - OpenAI 코드를 제거한다.
  - 꼬리질문만 서버의 소형 한국어 언어 모델로 만든다.
  - 무료 서버(Oracle Cloud 상시 무료)에 배포할 준비를 한다.
- **C 시선 방향.**
  - 면접 전에 10초 동안 기준을 잡는다.
  - 답변마다 시선 방향(정면·위·아래·왼쪽·오른쪽·판정 못 함)의 비율을 회고에 보인다.
  - 개발용 실험실에서 사용자가 직접 3회 실측해 기준을 넘을 때만 제품 화면에 연다.

**하지 않는 것**
- 팀원 소유 코드를 직접 수정하지 않는다. 대상: `Profile.tsx`, `archiveFields.ts`, 로그인·대시보드·Apply, 공용 CSS, seungxa 확장. 필요한 변경은 문서로 제안한다.
- 외부에 영향을 주는 일은 사용자 승인 없이 하지 않는다: 팀 Supabase에 SQL 실행, PR #1 머지, 팀 저장소에 push.
- AI 코칭 판정, 디브리프 요약, 맞춤 질문 생성을 로컬 모델로 옮기지 않는다. 코칭은 규칙 기반 기본 점검, 질문은 템플릿으로 둔다.
- 브라우저 안 전사·언어 모델(WebGPU 등)은 하지 않는다. 나중 과제다.
- 시선으로는 다음을 하지 않는다: 화면과 카메라 구별, 화면 좌표 추정, 감정·자신감·집중도·정직성 추정, 점수화.
- 동시 사용자가 늘어날 때의 확장은 하지 않는다. 한 번에 하나씩 처리하고 나머지는 기다리는 것으로 충분하다(사용자 결정).

**실패로 보는 것** (돌아가더라도 이러면 실패다)
- 녹음, 전사문, 얼굴 특징이 외부 API로 나간다.
- 실측 기준을 넘지 못했는데 시선 방향을 제품 화면에 보이거나, 실패를 성공처럼 보고한다.
- 팀 화면(로그인·프로필·대시보드)의 동작이나 모양이 바뀐다.
- 기존 기록(과거 AI 코칭 보고서, 디브리프 요약, AI 피드백)이 사라지거나 회고 화면에서 깨진다.

## 2. 제약

- **팀 frontend:** React 19, react-router 8, Vite 8, TypeScript 6. 기능 코드는 `frontend/src/features/practice-track/` 아래에만 둔다.
- **DB:** SQLite(로컬·테스트)와 Supabase Postgres 둘 다 계속 동작해야 한다(D-02, D-12).
  - 이번 작업은 **DB 스키마를 바꾸지 않는다.**
  - `ai_feedback`, 디브리프 요약 등의 컬럼은 남겨 두고 새로 쓰지만 않는다.
- **서버(Oracle Always Free A1):** ARM64, 2 OCPU, 메모리 12GB.
  - 7일 동안 CPU·네트워크·메모리 사용률이 모두 20% 미만이면 회수될 수 있다.
  - 대안은 Azure for Students $100 크레딧으로 4GB급 VM을 약 3~4달 쓰는 것이다.
- **서버 메모리 예산:** 전사(faster-whisper `base`, int8)와 꼬리질문 모델(약 1~1.3B, 4비트)을 합쳐 상주 3GB 이하.
- **외부 유료 API 호출 0회.** 모델 파일은 Hugging Face에서 처음 한 번 받아 캐시한다.
- **시선 계산:** 브라우저에서 기존 카메라 스트림과 MediaPipe 검출기 하나만 쓴다. 새 의존성은 없다. 결과는 탭 메모리에만 둔다(D-17, D-30, D-35).
- **사람이 해야 하는 일:**
  - 팀 Supabase 접속 정보를 받는다(팀원에게서).
  - Oracle에 가입한다(카드 인증 필요).
  - 시선을 3회 실측한다.
  - 팀 저장소 push·PR을 승인한다.

## 3. 검토한 방법과 고른 것

### 3.1 언어 모델·전사를 어디서 돌릴까
- **A. 사용자 노트북 브라우저 안** (transformers.js Whisper, WebLLM 1B 이하)
  - 좋은 점: 녹음이 노트북 밖으로 나가지 않고, 서버 계산 비용이 없다.
  - 대가:
    - 전사·꼬리질문 흐름을 자바스크립트로 다시 짜야 한다.
    - 처음 쓸 때 수백 MB를 내려받는다.
    - 그래픽 성능이 낮은 노트북에서는 느리다.
    - 1B 이하 모델의 한국어 품질이 불확실하다.
- **B. 팀 서버 한 곳 (선택)**
  - 좋은 점: 지금 파이썬 코드를 거의 그대로 쓰고, 사용자 기기와 상관없이 품질이 일정하다.
  - 대가: 메모리 4GB 이상 서버가 필요하고, 동시 사용자는 기다려야 한다.
- **C. 사용자 PC에 별도 프로그램 설치:** 설치를 두 번 해야 해서 제외했다.
- **크롬 내장 AI(Gemini Nano):** 한국어를 지원하지 않고 RAM 16GB·저장공간 22GB를 요구해서 제외했다.
- **고른 이유:** 남은 학기 안에 끝낼 수 있고 한국어 품질이 가장 낫다. 전사와 꼬리질문 부분을 갈아 끼울 수 있게 분리해서 나중에 A로 옮길 길을 남긴다.

### 3.2 남은 OpenAI 코드
- **(가) 완전히 제거:** 규칙과 템플릿만 남긴다.
- **(나) 꺼진 채 유지.**
- **(다) 로컬 언어 모델로 교체 (선택).** 범위는 **꼬리질문만**이다.
  - 코칭 판정과 디브리프는 형식에 맞춘 판정과 정확한 인용을 요구해서 소형 모델에 맞지 않는다.
  - 이미 규칙 기반 회고(R1 "한눈에 보기", 다시 연습할 답변 고르기)가 있다.
  - 그 밖의 OpenAI 코드는 (가)처럼 제거한다.

### 3.3 무료 서버
- **Oracle Always Free A1 (선택).** 2 OCPU·12GB이고 기한이 없다.
  - 위험 요소: 카드 인증, 지역에 자리가 없을 수 있음, 미사용 회수 규칙, ARM 빌드.
- **Azure for Students (대안).** 카드가 필요 없지만 크레딧이 떨어지면 멈춘다. 무료 VM은 1GB라 부족하다.
- **Google Cloud Run:** 꺼졌다 켜질 때 모델을 다시 불러오느라 지연된다. 백그라운드 정리 작업(`purge_loop`, 디브리프 작업)과도 맞지 않아 제외했다.
- **Hugging Face Spaces:** 2026년 현재 Docker 서버는 유료 플랜이 필요해 제외했다.
- **Render·Koyeb:** 메모리가 512MB라 제외했다.

### 3.4 시선 방향
- **① 보정 없이 답변 중 중간값과 비교:** 답변 내내 아래를 보면 그게 '정면'이 되어, 대본 읽기를 놓친다.
- **② 시작 전 10초 기준 잡기 (선택):** 다섯 방향을 2초씩 본다. 개인차를 반영하고, 처음부터 아래를 보는 습관도 잡는다.
- **③ 기존 G2 화면 좌표를 3×3 칸으로 나누기:** 보정이 길고, 오차가 화면 너비의 19%라 칸 경계에서 자주 틀린다.
- **고른 이유:** 큰 방향만 가리면 되므로, 웹캠 정밀도 안에서 개인 기준만 있으면 될 가능성이 크다. 정밀 판정을 노린 G1·G2와는 문제가 다르다.

## 4. 설계

### 4.1 A — 팀 통합 준비

**A1. 작업 기준**
- 앞으로의 작업은 팀 저장소에서 PR #1 브랜치 위에 쌓는다.
- 개인 저장소 `leejw0010/Jobseeker`의 PR #6은 기록용으로 두고 머지하지 않는다. 닫을지는 사용자가 정한다.
- PR #1이 `feature/frontend`에 머지되면 이후 브랜치는 그 위로 rebase한다.

**A2. 팀 Supabase 적용 묶음** (팀 프로젝트에는 아무것도 실행하지 않는다)

배경:
- 팀 프로젝트에는 이미 `profiles` 테이블이 있을 수 있다.
- 클라이언트 코드 기준으로 `profiles`는 `user_id`·`archive`·`updated_at`을 쓴다(통합 안내 6절).
- 그러므로 `schema.sql`(새 프로젝트용)을 그대로 실행하지 않는다.

만들 것:
- **사전 점검 SQL** (읽기 전용 카탈로그 조회):
  - 우리가 만들 테이블·인덱스·정책·버킷과 같은 이름이 이미 있는가.
  - `profiles`의 실제 컬럼과 RLS는 어떤가.
  - 결과를 사람이 읽고 다음 단계를 정한다.
- **적용 순서 문서:**
  - `migrations/*.sql`을 어떤 순서로 실행하는지.
  - 기능 플래그(`PRACTICE_INSIGHTS_ENABLED`)와 어떤 migration이 짝인지.
  - 비공개 `recordings` 버킷을 만드는 방법.
  - 되돌리는 방법: 플래그를 끄고 이전 앱으로 돌아간다. 데이터를 삭제하는 down migration은 만들지 않는다.
- **연결 점검 도구** (`scripts/practice-track/` 아래, 읽기만 한다). 환경 변수로 받은 접속 정보로 다음을 확인한다.
  - DB 연결.
  - 필요한 테이블·컬럼이 있는가.
  - `recordings` 버킷이 있고 비공개인가.
  - JWT 검증: JWKS 공개키를 조회할 수 있는가, 또는 HS256 secret이 설정됐는가.
  - 실패 항목은 사유와 함께 출력한다.
- **`backend/.env.example`의 Supabase 연결 예시 보강.**
  - 구현 때 공식 문서로 확인할 것: Supabase 직결 주소가 IPv6 전용이면 Oracle VM(IPv4)에서는 세션 풀러 주소를 써야 할 수 있다.

**A3. 크롬 확장 통합 계약 문서** (코드 수정 없음)
- seungxa 확장(JobSeeker Apply 0.7.0)이 지원서 제출을 확인하면 기존 `POST /track/sync`를 부르는 방법을 정리한다.
  - 요청 본문.
  - `submitted`를 명시하는 규칙.
  - 로그인 토큰을 전달하는 방법.
  - 응답의 `application_id`로 Track·Practice를 여는 방법.
- 우리 `extension-track`(공고 저장 팝업)의 기능을 seungxa 확장 안으로 옮기는 방안을 정리한다.
- 공유할 사항: seungxa 확장의 선택 기능인 AI 판단(Claude/OpenAI API 키)이 팀의 "외부 API 미사용" 결정과 어긋난다.

### 4.2 B — OpenAI 제거와 로컬 꼬리질문

**B1. 백엔드에서 제거할 것**
- **`llm.py`:**
  - 제거: OpenAI 호출(`_chat`, `_chat_json`), AI 질문 생성, `transcribe`, `feedback`, `debrief_summary`.
  - 남김: 템플릿 질문 생성, 다른 모듈이 쓰는 인용 확인 유틸(`verify_quote` 등).
  - 모듈 이름을 바꿀지는 빌더가 정한다.
- **`coaching.build_report`:**
  - AI 경로를 제거하고 항상 규칙 기반 기본 점검(`_basic`)을 쓴다.
  - AI 역량 근거(`competency_evidence`)와 `PRACTICE_COMPETENCY_EVIDENCE_ENABLED`를 제거한다.
  - 꼬리질문 문장만 B3의 로컬 모델 결과로 채운다.
- **`debrief.py`:**
  - AI 세션 요약을 제거한다.
  - 자동 디브리프 작업은 두 가지만 한다: 코칭 보고서가 없는 답변의 기본 점검, 다시 연습할 답변 고르기.
- **`stt.py`:** OpenAI 제공자를 제거한다(`local`/`off`만 남김).
- **`routers/practice.py`:** `POST /answers/{id}/feedback`를 제거한다. 기존에 저장된 `ai_feedback` 값은 응답에 그대로 둔다.
- **`config.py`:** `OPENAI_*` 설정을 제거한다. 환경에 `OPENAI_API_KEY`가 남아 있으면 "사용하지 않음" 경고 로그만 남기고 무시한다.
- **`main.py`의 `/health`:** `openai` 필드를 꼬리질문 모델 상태(사용 가능 여부, 모델 이름, 로딩 상태)로 바꾼다.
- **기존 기록:**
  - `method: "ai"`인 과거 코칭 보고서, 과거 디브리프 요약, `ai_feedback`은 지금처럼 읽기 전용으로 보인다.
  - 이미 있는 legacy 표시 규칙(D-32)을 유지한다.
- **테스트:**
  - OpenAI 경로 테스트는 삭제하거나 교체한다.
  - **외부 호출 0회** 테스트를 추가한다. 앱 전체 흐름(질문 생성 → 답변 → 코칭 → 꼬리질문 → 종료·디브리프)을 돌리는 동안 외부 HTTP 요청이 0회임을 확인한다.

**B2. 프런트엔드에서 바꿀 것**
- 대상 화면: 설정(`PracticeSettings`), 동의(`ConsentPanel`), 회고(`SessionReview`), 카메라(`CameraPanel`).
- "OpenAI로 보내요" 문구를 실제와 맞게 고친다: 녹음과 전사문은 우리 서버에서만 처리한다.
- AI 피드백 버튼, 키가 없을 때 뜨는 안내, `/health.openai`에 의존하던 부분을 정리한다.

**B3. 로컬 꼬리질문**
- **모델 우선순위:**
  - 1순위: Kakao `kanana-2-1.3b-instruct`의 GGUF 4비트(Kanana Open License, 상업 사용 가능하지만 조건 있음).
  - 2순위: LG `EXAONE-4.0-1.2B` 공식 GGUF.
- **첫 작업에서 확인할 것:**
  - 1.3B는 구조(`kanana2_tiny`)가 새롭다. 커뮤니티 GGUF는 있지만 `llama-cpp-python`이 실제로 불러와 한국어를 생성하는지는 확인되지 않았다. 안 되면 2순위로 바꾸고 결정을 기록한다.
  - 라이선스의 표기 의무를 확인해 README에 적는다.
- **실행 방식:**
  - `llama-cpp-python`으로 서버 프로세스 안에서 불러온다. 별도 서버 프로그램은 쓰지 않는다.
  - 한 번 불러와 재사용한다. 기본은 첫 요청 때 불러오고, 서버 시작 때 미리 불러오는 설정을 둔다(배포 기본값은 켬, B4의 회수 방지).
  - 한 번에 하나씩 처리한다. 전사의 `Semaphore` 패턴과 같다.
  - 대기 시간 상한을 넘으면 대체 문장으로 넘어간다.
- **설정:**
  - 켜고 끄기: `off` / `local`. 테스트 기본값은 `off`이고 가짜 모델로 바꿔 끼운다.
  - 모델 저장소·파일 이름, 모델 캐시 폴더, CPU 스레드 수, 생성 시간 상한, 다운로드 허용 여부.
- **입력:** 질문, 답변 전사문(길이 상한), 기본 점검이 고른 초점(구체성 등).
- **출력:** 꼬리질문 한 문장.
- **검증:** 한국어인지, 길이 범위, 물음표나 요청형 어미로 끝나는지, 금지 내용이 없는지(감정·외모·성격 언급, 전사문에 없는 수치).
  - 검증에 실패하거나, 시간이 초과되거나, 모델이 없으면 지금의 고정 문장 꼬리질문을 쓰고 대체 사유를 기록한다.
- **생성 시점:**
  - 지금처럼 꼬리질문 요청(`POST /answers/{id}/followup`)에서 보고서가 없을 때 만드는 `_report` 단계에서 생성한다. API는 바뀌지 않는다.
  - 세션 잠금을 잡은 동안에는 모델을 호출하지 않는다는 기존 규칙을 지킨다.
  - 화면에는 "꼬리질문 만드는 중"을 보인다. 예상 10~30초.
  - 전사가 끝나는 즉시 미리 만들어 두는 최적화는 빌더가 판단한다.
- **품질 확인 (사람이 읽는다):**
  - 이 PC에서 2스레드로 Oracle 2 OCPU를 흉내 내 속도를 잰다.
  - 준비한 답변 예시 10개로 생성 결과를 사용자가 읽고 쓸 만한지 판단한다.
  - 자동 점수로 품질을 주장하지 않는다.
- **의존성:**
  - `llama-cpp-python`은 컴파일이 필요해서 기본 `requirements.txt`와 분리한다. 서버 설치용 별도 파일을 두고, 테스트와 CI는 설치 없이 돈다. 이름은 빌더가 정한다.

**B4. 무료 서버 배포 준비** (실제 가입·생성은 사용자가 한다)
- **대상:** Oracle A1, Ubuntu ARM64.
- **배포 문서와 스크립트:**
  - 시스템 패키지, 파이썬 가상환경, ARM에서 `llama-cpp-python` 빌드, `faster-whisper` 설치.
  - 모델 미리 받기 명령.
  - systemd 서비스(재시작 정책 포함).
  - 환경 변수 예시: Supabase, 모델, CORS.
- **HTTPS:**
  - 팀 웹과 확장이 https에서 API를 부르므로 필요하다.
  - 리버스 프록시로 자동 인증서를 받는다.
  - 도메인은 무료 방식(예: IP 기반 와일드카드 DNS나 무료 동적 DNS) 중에서 빌더가 고르고, 사용자가 할 일을 문서에 적는다.
- **CORS:** 팀 웹 origin과 확장 origin(`chrome-extension://<id>`)을 허용한다.
- **회수 방지 메모:**
  - 모델을 메모리에 상주시켜 메모리 사용률 20% 조건에 걸리지 않게 한다. 근거는 사용 중 메모리를 재서 적는다.
  - 그래도 회수되면 다시 만드는 절차를 적는다.
- **동시성:**
  - 전사와 꼬리질문은 각각 한 번에 하나씩 처리한다. 대기 시간 상한을 넘으면 실패로 응답하고 다시 시도하라고 안내한다(전사는 기존 동작).
  - 실제 동시 사용자 부하 시험은 하지 않는다.

### 4.3 C — 시선 방향 분석

**C1. 판정 모듈** (순수 계산, `video/gaze/` 아래 새 파일)
- **입력:** 기존 `features.ts`의 특징.
  - 홍채 위치 `ex`·`ey`, 눈 뜬 정도 `open`, 고개 방향 `hx`·`hy`.
  - 얼굴 위치·크기 `faceX`·`faceY`·`scale`.
- **기준(보정 결과):**
  - 다섯 방향(가운데·위·아래·왼쪽·오른쪽)의 특징 평균과 흩어짐.
  - 기준 자세(얼굴 위치·크기).
  - 기준 눈 뜬 정도.
- **판정:**
  - 매 표본(기존 250ms 격자 그대로, 주기는 바꾸지 않음)의 특징을 가운데 기준과 비교한다.
  - 보정에서 잰 방향별 이동량에 비춰 가장 가까운 방향으로 판정하고, 충분히 벗어나지 않았으면 '정면'으로 둔다.
  - 홍채와 고개를 함께 쓴다. 고개만 돌리거나 눈만 돌려도 방향으로 잡는다.
  - 결합 방식(가중 합, 표준화 후 최근접 등)과 경계값은 빌더가 정하되, 실험실 결과로 조정할 수 있게 상수를 한곳에 모은다.
- **판정 못 함 (사유 포함):**
  - 얼굴 없음.
  - 눈 감김(`open`이 기준의 0.5배 미만, 기존 `OPEN_MIN_RATIO`).
  - 특징 무효(기존 `FeatureInvalid` 사유).
  - 기준 자세에서 크게 벗어남(기존 `SCALE_TOL`·`POS_TOL`).
- **흔들림 줄이기:** 짧은 창(약 0.75초)의 다수결로 평활한다. 창 길이는 빌더가 정한다.

**C2. 기준 잡기 단계** (면접 진행 화면)
- **언제:** 면접 진행 화면(`SessionRunner`)에서 카메라가 켜져 있고 첫 답변을 시작하기 전.
- **화면:** "시선 기준 잡기(약 10초)"를 보인다. 점이 가운데 → 위 → 아래 → 왼쪽 → 오른쪽 순서로 나타난다.
  - 점 하나: 안정 0.7초 + 수집 1.3초.
  - 위·아래·왼쪽·오른쪽 점은 뷰포트 가장자리 근처에 둔다.
- **품질 점검:**
  - 방향끼리 충분히 갈리는지, 유효 표본이 충분한지 본다.
  - 부족하면 "다시 하기 / 건너뛰기"를 보인다.
  - 건너뛰면 그 세션은 시선 방향을 재지 않는다. 고개 방향 지표(D)는 지금처럼 동작한다.
- **유지와 무효화:**
  - 기준은 같은 세션 동안 탭 메모리에 둔다.
  - 자세가 크게 바뀌면 '판정 못 함'이 늘어나므로, 답변 사이에 "기준 다시 잡기"를 안내한다.
  - 창 크기·배율·카메라 해상도가 바뀌면 기준을 무효로 한다(G의 기존 규칙과 같음).

**C3. 답변별 요약**
- **수집 시점:** 기존 `beginSegment`/`endSegment`와 같은 구간에 프레임 구독(`subscribeFrames`)으로 판정을 모은다.
- **요약 내용:**
  - 방향별 시간과 비율.
  - 판정 못 함 시간과 사유별 시간.
  - 방향이 바뀐 횟수.
  - 가장 긴 '아래' 구간.
- **보관:** 기존 영상 요약처럼 탭 메모리에만 둔다(녹음 revision 키 포함). 서버로 보내지 않는다.

**C4. 회고 표시** (기능 플래그 뒤)
- **위치:** `VideoReportCard`에 "시선 방향" 부분을 더한다.
- **보이는 것:**
  - 방향별 막대.
  - 해석 문구. 예: "아래 18% — 대본이나 키보드를 본 시간일 수 있어요".
  - 판정 못 함 비율.
  - 한계 안내: 화면과 카메라는 구별하지 않는다, 평가나 점수가 아니다.
- **플래그:** `VITE_GAZE_DIRECTION`(이름은 빌더가 정함). 기본은 꺼짐이고, C5의 통과 기준을 넘은 뒤에만 켠다.
- **문구 수정:** 플래그가 켜지면 카메라 동의 문구의 "시선 추적이 아니에요"를 실제 동작에 맞게 고친다.

**C5. 실험실에 '방향' 실험 추가** (`/dev/gaze-lab`, 개발 전용)
- **진행:**
  1. 기준 잡기(C2와 같은 코드).
  2. 무작위 순서로 방향을 지시한다(가운데 포함, 방향마다 3회, 2초씩).
  3. 두 조건으로 반복한다: 고개를 고정하고 눈만 움직이기, 자연스럽게 고개와 함께 움직이기.
  4. "종이 대본을 아래에 두고 읽기" 구간을 별도로 둔다.
- **결과:**
  - 방향별 정답률, 혼동표, 판정 못 함 비율과 사유.
  - 익명 집계 JSON 복사. 영상·좌표·특징점은 넣지 않는다.
- **통과 기준 (잠정, 제 판단 — 결과를 보고 사용자와 조정):**
  - 3회 중 2회 이상에서 다음을 모두 만족해야 한다.
  - 정면 ≥ 85%.
  - 아래 ≥ 80%.
  - 위·왼쪽·오른쪽 각각 ≥ 70%.
  - 정면을 아래로 오판 ≤ 10%.
  - 판정 못 함 ≤ 15%.
- **기존 실험:** G1·G2 실험은 그대로 둔다. 제품에는 쓰지 않는다.

**C6. 테스트**
- 합성 얼굴(`synthetic.ts`)로 계산 테스트를 한다: 방향별 판정, 판정 못 함 사유, 자세 무효화, 평활.
- 가짜 검출기로 E2E를 한다: 기준 잡기 → 답변 → 회고에 방향 비율 표시(플래그 켬). 플래그를 끄면 아무것도 보이지 않아야 한다.

## 5. 진행 순서

1. **A1** 작업 기준(이 브랜치).
2. **C5 실험실과 C1 판정 모듈을 먼저.** 사용자가 실측을 돌리는 동안 나머지 작업을 진행할 수 있다.
3. **B1·B2** OpenAI 제거 → **B3** 로컬 꼬리질문.
4. **B4** 배포 준비, **A2** Supabase 묶음, **A3** 확장 계약 문서.
5. **C2~C4** 기준 잡기, 요약, 회고. 실측 통과 시 플래그를 켠다.

갈래마다 구현 계획을 따로 쓰고, 커밋은 갈래별로 나눈다. 팀 저장소 push와 PR 대상(`feature/frontend` 또는 PR #1 브랜치)은 PR #1의 상태를 보고 사용자 승인 후 정한다.

## 8. 이 대화에서 사용자가 정한 것 (2026-11-14)

- 팀 저장소로 합치는 것을 전제로, 우리 쪽에서 고칠 수 있는 것부터 고친다.
